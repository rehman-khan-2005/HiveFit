## What was done

See [timeline v0.5](../timeline.md#v05--23-november-2026--present).

**The 50% cutoff could not be implemented as asked.** Checking it first showed
that every real listing scores below 35%, so the cutoff would have hidden the
entire list. Three candidate fixes to the scale were measured and rejected.
Postings are now banded relative to the set being compared — green, amber, grey
— which is what the "only show green jobs or orange jobs" note suggested
independently. Full write-up:
[findings/scoring-ceiling.md](../findings/scoring-ceiling.md).

**Two data bugs were found while measuring**, and they matter more than the
formula: descriptions were storing their own HTML markup, and three quarters of
the pool has no description to score.
[findings/data-quality.md](../findings/data-quality.md).

**Four preferences in one dropdown** — match strength, hide weak matches, where
you will work, how much detail. Stored on the account rather than the device.

**"How these employers spell it."** The keyword-search point, built as 33 skill
alias groups: a recruiter types "Kubernetes" and a resume saying "k8s" is not in
the result set. Only fires on skills the resume already claims, and the advice
is always additive.

**On-demand availability check**, at the moment the user is about to spend an
hour tailoring to a posting.

## Not built, deliberately

**The user survey**, and **defaults inferred from prior experience.** Both are
research questions — what people actually want to hide — and the preferences now
in place are what the survey would be run *with*. The dropdown logs nothing yet;
if the survey should produce data rather than opinions, instrumenting the
preference changes is the prerequisite.
